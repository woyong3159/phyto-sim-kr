# KNOWN_LIMITS — 알려진 한계

## Phase 0 자기 반박(V5)에서 찾은 것

### L1. 지금은 시뮬레이터가 아니다 — 시계만 흐른다
재배자가 보면 가장 먼저 "작물이 없다"고 느낄 것이다. 맞다. Phase 0는 뼈대이고, 생리·환경 계산은 0줄이다.
가짜 숫자를 채워 넣지 않기 위해 자리표시 화면에는 값이 하나도 없다. → Phase 1부터 해소.

### L2. "비트 단위로 같은 결과"는 아직 같은 기기 안에서만 보장된다
난수는 정수 연산만 써서 모든 기기에서 같다. 그러나 Phase 1부터 쓰게 될 exp·log·pow·sin 같은 수학 함수는
브라우저 엔진(아이폰 Safari와 PC Chrome)에 따라 마지막 자릿수가 다를 수 있다. 그러면 아이폰에서 내보낸 세이브를
PC에서 재생할 때 결과가 미세하게 갈릴 수 있다.
→ 대응: Phase 1에서 엔진 전용 수학 함수를 자체 구현(기기 무관)하고, 스냅샷 지문을 대조해 어긋남을 감지한다.

### L3. WebKit(사파리 엔진) 검증을 이 작업 환경에서 직접 돌리지 못했다
작업 환경의 네트워크 제한으로 Playwright WebKit을 내려받을 수 없었다. 이번 스크린샷과 화면 테스트는
같은 iPhone 14 화면 크기·터치 조건을 Chrome 엔진으로 흉내 낸 대체 검증이다.
→ 대응: 배포 파이프라인(GitHub Actions)에 WebKit 테스트가 들어 있어, 코드를 올릴 때마다 정식 검증이 돈다.
   실기기 확인도 체크리스트로 요청한다.

### L4. 안전 영역은 "값을 넣어서" 확인했다
에뮬레이터는 노치·홈 인디케이터 여백을 0으로 준다. 실제 아이폰 값(위 47pt, 아래 34pt)을 주입해 레이아웃을
확인했지만, 실제 기기에서의 모습(특히 홈 화면 앱 전체화면에서 상태 표시줄과 겹치지 않는지)은 실기기로만 확정된다.

### L5. 30일/초 성능은 엔진이 비어 있을 때의 이야기다
지금은 스텝이 거의 공짜라 30일/초(초당 720스텝)가 쉽게 나온다. 미기상 10분 서브스텝과 작물 계산이 들어오면
아이폰에서 같은 배속이 나올지는 Phase 1–2에서 측정해야 안다.

### L6. 아이폰이 앱을 즉시 죽이면 마지막 0.1초가 사라질 수 있다
화면이 가려질 때 "지금 아는 시각"으로 즉시 저장하고, 워커의 확정 시각이 오면 한 번 더 저장한다.
두 번째 저장 전에 앱이 멈추면 최대 0.1초(30일/초 배속 기준 게임 약 3일)만큼 앞 시각으로 되돌아간다.
사용자 조치는 로그에 남으므로 잃지 않고, 다시 재생하면 같은 결과가 나온다.

### L7. 아이폰 저장소 정책
- 사파리 탭에서 쓴 세이브와 홈 화면 앱의 세이브는 서로 다른 저장 공간이다. 홈 화면에 추가한 뒤에 시작하는 것이 맞다.
- iOS는 오래 쓰지 않은 사이트의 저장 데이터를 정리할 수 있다. 홈 화면 앱은 이 정책에서 더 안전하지만,
  "가끔 한 작기씩" 쓰는 도구인 만큼 중요한 작기는 더보기 → 내보내기로 파일 백업을 권한다.
- 영구 저장(navigator.storage.persist) 허용 여부는 기기가 결정하며, 타이틀 화면의 시스템 점검에 결과를 그대로 표시한다.

### L8. 엔진 모듈은 한 파일에 스텁으로 모여 있다
헌법 6항의 폴더(crop/, rootzone/ …)는 각 Phase에서 구현하면서 분리한다. 지금 빈 폴더만 만들어 두는 것은 의미가 없다고 판단했다.
